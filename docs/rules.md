# Destiny's rules

This table lists the rules of destiny's behaviour that exact-ballpark is held to. Each rule has an identifier, a one-line statement, its location in destiny's source (and, where it applies, in carbonengine/math or DirectXMath), its status, and the test files that check it. The identifiers also appear in the package's docstrings and tests, so a reader can go from any of them to the line of destiny's code it reproduces.

Every location is at the pinned commits (`provenance.md`): destiny `114e89fa`, carbonengine/math `82733220`, DirectXMath `f5d82574`. Line numbers are those of the pinned files. A location in `python/destiny/test/` is one of destiny's own published tests, whose vectors the reference reproduces.

## How to read the status

- **passing (compiled code):** the scalar reference reproduces destiny's C++ for this rule, compiled from the pinned source by the conformance kit, and the listed tests compare every value exactly.
- **passing (test vectors):** the reference reproduces the expected values of destiny's own published tests for this rule (destiny's Python test suite).
- **implemented, not passing:** the reference implements the rule, but the tests do not hold all of it to destiny. The reason is given in the row, and `limits.md` repeats it.

Where a batched park or a CUDA kernel implements a rule, the listed tests also hold it to the reference bit for bit (`exactness.md`). A rule's tests may include the batched and kernel tests of every park it appears in.

**105 rules:** 93 passing (compiled code), 6 passing (test vectors), 4 implemented, not passing (compiled code), 2 implemented, not passing (test vectors).
